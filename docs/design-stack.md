## Problem Statement

The user wants to build an app to learn and practice drums, modeled on a discontinued
discontinued classic standalone drum-tutor. Primary motivation is personal use plus a circle
of drummer friends, with a stretch goal of a $2 tablet app on iOS and Android. A
secondary personal goal is to level up AWS/cloud skills as part of the build.

The full functional scope lives in `scope.md`. This document focuses on the
**technology stack decision** that will support that scope.

## What Makes This Cool

- **Replaces an extinct tool.** The classic standalone drum-tutor was discontinued.
  Existing owners have nowhere to go for an equivalent experience.
- **Two specific wedges vs the dominant competitor (subscription tutor).** subscription tutor
  partnered with Roland but has two documented user complaints surfaced
  during this office-hours session:
  1. No way to upload custom MIDI or Guitar Pro files.
  2. No Android app.
  This product addresses both from day one.
- **First-class custom song upload.** Drummers who already practice songs they
  love (not just licensed subscription tutor content) are underserved today.
- **Real-time visual feedback** with timing categories (perfect / early / late /
  missed / extra) styled after standard drum-kit notation.

## Constraints

- **Primary devices:** iPad and Android tablet are co-primary (user plays drums
  on iPad daily; Android tablet is the wedge audience).
- **Latency target:** <20ms perceived round-trip on iPad/Android/Mac.
  Windows v1 may run at ~10-20ms via PWA; pro-grade Windows latency is out of

- **Developer expertise:** Web stack (TypeScript + JS). No Dart, Swift, or

- **Distribution channels:** App Store (iPad + iOS), Play Store (Android),

- **AWS/cloud component is required**, not optional — the user wants this as a

- **Offline-first is a CORE constraint, not nice-to-have.** The app must work

- **Career angle:** the backend doubles as a system-design portfolio piece.
  Choices favor "rich enough to whiteboard and defend in a Staff FE interview"
  over "minimum required to ship."

## The Critical Architectural Decision: Where Hit Scoring Lives

This is the load-bearing architectural choice the rest of the stack hangs on.

**Decision: hit scoring runs NATIVE-SIDE in the Capacitor MIDI bridge.**
The native plugin loads a per-song tick map at song start, captures MIDI
events directly from CoreMIDI / `android.media.midi`, scores each event
against the tick map, and only sends `{noteId, verdict, ts, velocity}`
events across the JS bridge to React/Vue for rendering.

Why: every MIDI event that has to cross the JS bridge for scoring eats
~1-5ms of bridge overhead plus Web Audio output scheduling latency. Doing
scoring in native code keeps the *perceived correctness* of the hit under
10ms; the visual feedback can lag the actual hit by 15-30ms and still feel
right because the human ear catches the timing, not the eye.

For PWA (Windows/Mac/Linux desktop where there is no native bridge), scoring
runs in JS using the Web MIDI API. Latency budget is looser (10-25ms) and
acceptable for v1.

## Approaches Considered

### Approach A: Capacitor + AlphaTab + PWA (selected)

**Stack (aligned with user's Phase 0 fork + AWS brainstorm):**
- Frontend: TypeScript + **React 19** + Tailwind + Vite
- Music core: **`@coderline/alphatab@^1.8.1`** (MPL-2.0; Guitar Pro
  parsing, standard drum notation, `AlphaSynth` audio synth engine)
- **Friendly notation view (falling-notes-style falling notes):** PixiJS
  on a separate canvas, fed from the same tick map AlphaTab uses.
  PixiJS chosen over plain Canvas 2D for animation throughput on dense
  drum charts (kick + 2 toms + snare + hi-hat + ride + crash + ghost
  notes = a lot of moving sprites per second).
- Audio scheduling: `tone@^15` for metronome and count-in. AlphaSynth is
  the **timeline master**; `Tone.Transport.seconds` is periodically
  re-synced from AlphaSynth's `positionChanged` callbacks (drift
  correction, not true slaving — AlphaSynth doesn't export a sample-
  accurate clock). Metronome ticks are scheduled in beat coordinates from
  AlphaSynth position, not from `Tone.Transport` time, to avoid drift on
  backgrounded iOS AudioContexts.
- MIDI input:
  - **iPad shell:** custom Swift Capacitor plugin wrapping CoreMIDI. Scoring
    runs native-side against a pre-loaded tick map. Emits verdict events to JS.
  - **Android shell:** custom Kotlin Capacitor plugin wrapping
    `android.media.midi`. Same architecture as iPad.
  - **Desktop PWA:** Web MIDI API directly in JS. Scoring runs in JS.
  - **MIDI mapping (multi-zone e-drums):** per the user's
    `MIDI_MAPPING_PLAN_SUMMARY.md`. Mapping is applied BEFORE scoring
    (native side for Capacitor shells, JS side for PWA). Presets for
    Yamaha DTX, Roland TD-50; user-editable custom mapping persisted to
    LocalStorage + synced via RxDB/Legend-State.
- File parsing: AlphaTab for `.gp/.gpx/.gp5`; `@tonejs/midi@^2` for `.mid`
- **Offline-first sync:** **RxDB or Legend-State** (TBD in Phase 0+) handles
  client-side persistence + replication protocol. Server is two Lambdas:
  `pull(checkpoint)` queries a DynamoDB GSI for changes since the checkpoint;
  `push(changeRows)` does conditional writes (LWW on `updatedAt`) and
  returns conflicts. Soft-delete tombstones with DynamoDB TTL (~30 days).
- **AWS backend (raw services, Pulumi TypeScript IaC):**
  - **Lambda Function URL** (no API Gateway). JWT verified in-handler via
    `aws-jwt-verify` against Cognito user pool.
  - **DynamoDB** single-table design with GSI on `(USER#sub, updatedAt)`
    for sync change-feed. Streams enabled for projection side-effects.
  - **Cognito** Hosted UI + PKCE + Google federation (v1). Apple
    federation added with iOS shell (Apple requires it on App Store if
    any social login is offered). GitHub federation deferred (needs OIDC
    bridge).
  - **SQS + SNS fan-out → consumer Lambda → S3 (Parquet) → Athena** for
    usage analytics. DynamoDB is wrong here (no aggregation).
  - **CloudFront + OAC** in front of a private S3 bucket for the PWA
    static bundle. Always-Free 1 TB/month covers solo dev cost easily.
- **Observability split:**
  - Backend SRE: **CloudWatch + X-Ray** (Lambda errors/duration/throttles,
    SQS age-of-oldest-message, DynamoDB ThrottledRequests; SLOs + burn-rate
    composite alarms).
  - Client errors: **Sentry** free tier (not CloudWatch RUM — not free).
  - Usage analytics: the SQS → S3 → Athena pipeline.
- **IaC:** `pulumi@^3` TypeScript. Terraform literacy as a separate
  afternoon — concepts transfer 1:1; interviews ask concepts.
- **Build:** Vite + Capacitor CLI 6.x.
- **Distribution:** Xcode 16 → App Store; Android Studio → Play Store;
  Vite static build → CloudFront + S3 for PWA.

**Custom rendering layer on top of AlphaTab:**
AlphaTab renders the score as SVG. For per-note feedback (green/orange/purple
circles, red cross at the *actually-hit* staff position rather than the
expected one), we draw a separate absolutely-positioned SVG overlay aligned
to AlphaTab's note bounding boxes. Hit-position lookup uses AlphaTab's
`Renderer.boundsLookup` API to map staff lines (e.g. snare line, ride space)
to pixel coordinates.

**Required AlphaTab setting:** `core.includeNoteBounds = true` (opt-in;
adds render-time cost on dense drum scores — measure in Phase 0). Without
this, `boundsLookup` returns bar/beat bounds but not per-note bounds, which
breaks the extra-hit positioning feature.

**Hit-detection timing source:**
`AlphaSynth.positionChanged` (tick-based, locked to playback) drives the
scoring window. NOT DOM events. NOT `requestAnimationFrame`.

**Tick map format (JS → native):** at song load, AlphaSynth's score is
walked once to produce a JSON array `[{tick, midiNote, lane, windowMs}, ...]`
passed to the native bridge via a single `loadSong(tickMap, scoringWindows)`
call. Bridge acks; thereafter MIDI events on the device are scored locally
in native code against the tick map.

**Scoring windows (initial v1 values, tunable in settings):**
- Perfect: ±25ms
- Early/Late: ±50ms (outside perfect but inside this band → orange/purple)
- Missed: any expected tick that elapsed +75ms with no hit
- Extra: any input that doesn't match an expected tick within ±75ms

**Per-instrument volume:**
`AlphaSynth.applyTrackVolume(trackIndex, gain)` handles per-stem mixing
(drums, guitar, bass) including "mute mine / solo mine" modes.

**Effort:** Medium-Large (4-8 months solo, weekend pace, to first playable
v1 across iPad + PWA; Android shell adds 6-10 weeks).
**Risk:** Medium-High. The Capacitor MIDI bridges must be written from scratch
(no shipping `@capacitor-community/midi` plugin exists as of 2026). For a
TypeScript-only developer with no prior Swift/Kotlin shipping experience,
budget **4-6 weeks per platform** for a production-quality bridge (includes
Apple MIDI entitlements, background audio session config, Android USB-MIDI
permission flow, hot-plug callbacks, edge-case device handling). A single-
device happy-path spike still fits in 1 week per platform.

**Important latency clarification:** The native scoring keeps the *verdict
event* (perfect/early/late) under ~10ms perceived. The *audio feedback for
the hit* (metronome click confirming the beat, any backing-track sound) still
goes through Web Audio inside the WebView and carries ~15-30ms output latency
on iOS. The drummer hears their own e-drum acoustically (or via the drum
module's monitor out) so the audio output latency only affects the metronome
and backing track, not the felt timing of their own playing. This is fine
for practice; it is NOT fine if you ever want to add "play along to the
sample of the original drum hit" — that would need a native audio output
path too.

**Pros:**
- Maps directly to the user's strongest skill (web TypeScript).
- One codebase ships to three distribution channels.
- AlphaTab covers Guitar Pro parsing, standard and drum notation rendering,
  and audio synth playback in one library.
- Raw CDK + Lambda + DynamoDB + S3 + Cognito cleanly satisfies the AWS
  learning goal.
- iPad latency target (5-10ms scoring via native CoreMIDI) hits the gold
  standard.

**Cons:**
- Two custom native bridges (~300-600 LoC Swift + ~300-600 LoC Kotlin) before
  iPad/Android shells are playable.
- Mac users get PWA only in v1.
- Web Audio latency on Win PWA varies by OS (~10-20ms acceptable for v1).

### Approach B: Flutter cross-platform native (rejected)

Dart + Flutter for iOS/Android/macOS/Windows. AlphaTab inside a Flutter
WebView for notation; `flutter_midi_command` for native MIDI.

**Why rejected:** Adds Dart learning curve before any output (1-2 months
delay), and the WebView-for-notation friction (event marshalling, scroll
sync, layout-pass mismatches) undercuts Flutter's "native everything"
appeal. Native Windows MIDI is the only real win, which is below v1's bar.

### Approach C: Pure web PWA (the Phase 0 spike, not the v1 stack)

Same web layer as A, no Capacitor. iPad Safari has no Web MIDI → degraded.
**Not viable as the v1 product** because iPad is the daily driver. **IS the
right Phase 0 spike**: stand up the web layer on Mac Chrome to validate
AlphaTab + Tone.js + Web MIDI before paying the Capacitor + native-bridge
cost.

## Recommended Approach

**Approach A — Capacitor + AlphaTab + PWA**, with the architectural
qualifiers from the section above:
1. Hit scoring runs **native-side** in the Capacitor MIDI bridges.
2. Tone.js is **slaved** to AlphaSynth's clock, not the other way around.
3. Per-note feedback is drawn on a **custom SVG overlay** aligned to
   AlphaTab's `boundsLookup`, not via AlphaTab's render hooks.
4. AWS layer is **raw services via CDK**, not Amplify.

Phase 0 spike (Approach C scope) precedes Phase 1 (Capacitor shells).

## Open Questions

1. **RxDB vs Legend-State for the sync client lib.** Both target AWS via a
   custom replication handler. RxDB has more drum-tutor-shaped features
   (encryption, attachments via S3, conflict UI primitives). Legend-State
   has a simpler API and tighter React integration. **Decide during
   Phase 1** with a thin spike of both against a stub DynamoDB.
2. **Capacitor MIDI bridge plugin: write it yourself.** No community
   plugin ships at production quality in 2026. Plan two parallel work
   streams: iOS Swift bridge (4-6 weeks) and Android Kotlin bridge (4-6
   weeks).
3. **MIDI 2.0 vs 1.0.** Most e-drum kits are MIDI 1.0 in 2026. Build for
   MIDI 1.0 first; the native bridges can be extended for MIDI 2.0 if
   user hardware demands it.
4. **Backing track sync (MP3/MP4/YouTube)** is scoped as nice-to-have, not
   v1. Punt to v1.5 — MP3 via Tone.js, MP4 via HTML5 video, YouTube via
   iframe API. Sync precision against MIDI scheduling needs measurement
   on iOS first.
5. **XState for the game-mode FSM** (idle → count-in → playing → paused →
   results). Optional rigor — speaks well in a Staff FE interview as
   "I modeled the gameplay lifecycle as an explicit state machine." Skip
   if it slows v1; revisit at v1.5.
6. **MPL-2.0 boundary discipline.** Phase 0 fork (alphaTabWebsite) is
   MPL-2.0. The production notation-hero repo starts clean and uses
   `@coderline/alphatab` only as an npm dependency. Patterns learned in
   the fork get reimplemented (clean-room rewrite). No source files cross
   the boundary. Document this in the production repo's README so any
   future contributor or App Store reviewer can verify.
