## 1. The decision

The admin CMS **is the same catalog UI + the same lambdas**, with write actions shown only to a signed-in admin. There is **no separate CMS app**.

This is already the locked direction in the catalog design (`catalog-flow-decisions.md`, 2026-06-13):

> *"CMS = the same UI, with admin-gated actions (Upload / Add / Edit). Lesson steps are authored on the same surface."*

**Why:** one component set and one backend to build and maintain; consistent design for free; you own all the CRUD code (good for the AWS portfolio). The cost — hand-building the create/edit forms instead of getting them free from React-Admin — is accepted.

---

## 2. Reuse map — components

The public catalog already has the surfaces. Admin = the **same surfaces** + gated actions. No second component set.

| Catalog surface (public) | CMS reuse (admin-gated) |
|---|---|
| List — Stitch table, single-row filters, search | Same list; admin rows also show **Edit** + **Delete** |
| **Upload** button (topbar, already admin-only) | The entry point to **Add** → the insert form |
| Item **detail** (+ "Your history") | Same detail; admin sees **Edit** + **Delete** |
| Add → CMS form → step editor (in `catalog-flow.html`) | The **insert / edit** form, reused as-is |

**Admin affordances (Upload / Add / Edit / Delete) appear only after the admin enters the password** (see §4). Everything else (browse, search, filter, detail, play) stays identical to the public app.

---

## 3. Reuse map — lambdas / backend

The CMS adds **write routes on the existing backend** — no new datastore.

| Lambda | Public (read) | Admin (write / admin-read) |
|---|---|---|
| **Catalog read API** (`K-3`) | `GET` list + detail + signed file URL — **published only** | **Gated admin mode** *(decision F1)*: the **same** lambda returns **all statuses** (draft / published / archived) when the admin password is present |
| **CRUD lambda** (`K-2`) | — | create, edit, **delete = archive**, **un-archive**, presigned upload |

- Same **Neon Postgres** tables (schema is locked).
- Same **S3** for notation files (presigned upload → quarantine → promote).
- The read API serves both planes from one codebase: public callers get published items; an authenticated admin call adds drafts + archived. Only the gated path exposes non-published rows, so drafts never leak publicly.

## 4. Access control — the password gate (interim)

Captured from this session: *simple password, can live in the lambda, must not be in the public repo.* Shape locked by **decision F2: one public site, password-checked writes** (not a separate admin deployment).

- **One public site** (the catalog). No separate admin app.
- **Admin affordances appear after the admin enters the password** — but this client-side reveal is **cosmetic**. The **lambda is the real gate.**
- **Password required on every write** (create / edit / delete / un-archive / upload) **and on the gated admin-read** (the mode that returns drafts + archived). Public reads (published only) stay open.
- **Simple shared password**, no Cognito yet. **Checked inside the lambda.**
- **Secret never in the repo** (repo is public): injected via **env var / SSM Parameter Store (SecureString)** at deploy — never committed, never baked into source.
- Client never persists the password beyond **`sessionStorage`**. **Constant-time** compare, **HTTPS only**.
- **Temporary by design:** the check is one clearly-marked seam, swapped later for real auth (Cognito JWT, or the edge CloudFront Basic-Auth from `cms-approach.md`).

> The existing plan ([`cms-approach.md`](../cms-approach.md), schema §12) already specifies edge **CloudFront Function Basic-Auth** + **SSM SecureString**. Same idea; for the one-site shape, the in-lambda check is the simpler start. Edge Basic-Auth + a separate admin deploy stays available as the portfolio-grade upgrade.

## 5. First slice — full add-a-song

The first build = the whole add loop, admin-gated:

1. **Upload** a song file (the existing admin-only Upload button) →
2. **Create** the `catalog_item` (insert form) →
3. **Edit** its fields →
4. **Delete** it (= **archive**, `status='archived'`) →
5. **Un-archive** it (`archived` → `draft`/`published`) *(decision F3 — no hide-only dead-end)*.

**Rules the form must respect (from the schema):**
- **Delete = archive** (`status='archived'`) — the schema never hard-deletes (§12). The button can say "Delete"; it archives underneath, and un-archive brings it back.
- **`source` is write-once** (set at ingest; not editable in the form).
- **Publish gates:** a lesson needs ≥1 exercise; a curated item needs a `license`.

**Acceptance (light):**
- A signed-in admin can upload → create → edit → archive → un-archive a song; changes persist to Neon; the file lands in S3; the public list reflects published items only.
- The admin list shows drafts + archived (via the gated read mode); the public list never does.
- Without the password, all write routes **and** the admin-read mode are rejected; public reads still work.
